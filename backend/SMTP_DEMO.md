# Gmail SMTP demo verification

The email providers load `.env` directly from the backend working directory when sending. No IDE dotenv plugin is required. Operating-system environment variables override local values, including blank values (which produce a configuration error). A missing file is allowed when the required environment variables exist.

Create your own local `backend/.env` containing `GMAIL_USERNAME`, `GMAIL_APP_PASSWORD`, and `APPLICATION_RECEIVER_EMAIL`. Use your Gmail app password, not your normal account password. Do not put values in source, classpath properties, command arguments, chat, or logs. This change does not create a real `.env` or package it into the JAR.

The parser supports UTF-8 `KEY=value` lines, blank lines, comments, optional `export `, and single/double quoted values. Unquoted inline comments require whitespace before `#`. Quoted values are literal: shell expansion, escapes, and multiline values are not supported. SMTP uses Gmail port 587, authentication, mandatory STARTTLS, certificate hostname verification, and 10-second connection/read/write timeouts.

1. From `backend`, run `git check-ignore .env .env.local .env.production`. Each must be ignored. Check the local file privately; never print it in diagnostic output.
2. Run `app.Main` in IntelliJ with Java 21 and the backend folder as working directory. Alternatively, from that directory run `mvn package` then `java -jar target/backend.jar`. Maven can also launch it with `mvn exec:java -Dexec.mainClass=app.Main` if the exec plugin is available. On this workstation Maven is at `C:\Users\Olive\.maven\maven-3.9.15\bin\mvn.cmd`. Existing database and application configuration must also be available. Check the existing `FRONTEND_URL` points to your demo frontend for chat and unsubscribe links.
3. Submit one authenticated `POST /applications` using the configured API prefix. Verify the application is stored and `APPLICATION_RECEIVER_EMAIL` receives a readable `application-{id}.pdf`. The applicant is not the receiver. If PDF generation or delivery fails, the existing API error behavior remains and the application stays stored; inspect the saved record before retrying to avoid a duplicate.
4. Send an `INDIVIDUAL` newsletter to one controlled test account with marketing consent, using a persisted template with supported placeholders. Verify personalized content and the unsubscribe link. Follow the link through the frontend, then send again: the account must be skipped. Avoid the full subscriber list. For a controlled failed replacement send, the previously delivered link must still work; successful replacement delivery retains the existing token-rotation behavior.
5. With exactly one chat administrator, send a customer message and an admin reply. Verify only that admin receives the customer notification and only that customer receives the reply notification. Emails contain a generic login link, never the message text. Marketing consent does not suppress these transactional notifications.
6. For a controlled failure check, temporarily remove the local SMTP password setting (ensure no process variable overrides it), then send one customer message and one admin reply. Both requests should return HTTP 201 with their saved message IDs and remain visible exactly once. Restore local configuration afterwards. A sanitized warning records notification failure; notifications are not retried automatically.
7. If delivery fails, report only the error category: missing/blank setting, invalid address, unreadable/malformed local file, or SMTP delivery failure. For SMTP failures, privately check Gmail app-password setup and network access to port 587. Never enable mail protocol debugging or print credentials/configuration/transport exception details.

Automated tests use temporary dummy settings, H2, and injected delivery functions. They do not read the developer's `.env`, connect to Gmail, or verify actual inbox delivery. SMTP acknowledgement cannot guarantee inbox placement.
